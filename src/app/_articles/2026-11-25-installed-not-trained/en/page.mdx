A language model can describe an algorithm and still be unable to run it. Shown worked solutions to
Tower of Hanoi and asked for the next size, the model we used solved four disks in one attempt out
of six, and five, six or seven disks in none of sixteen.[^1] Fine-tuned on the solutions for one to
six disks, it learned those sizes and nothing beyond them. The usual fix is to hand the work to an
outside tool.

We did something else. We treated the model as a machine you can install software on. The program is
not learned and not attached. It is written into weights the model already has, and from then on the
model runs it natively, one token at a time.

> **The rule.** No training of any kind. Every number we changed is a closed-form function of the
> model's existing weights and a small table that describes the program. No gradients, no fitting to
> examples, no search over what to write.

There are two builds, and each result below says which it comes from. **The patch** rewrites one
attention head in the first layer. It is a file you apply to the unmodified model and take off
again. A person starts it by typing one line. **The launchable build** does the same computation but
hands over its answer differently, which lets the model start the program on its own. It is not a
small file: it nudges about a quarter of the model's numbers, each by a tiny amount. Most of this
article is about the patch. The last third is about why the model could not launch it, and what
fixed that.

## The one loop a language model has

Hand-written weights that run an algorithm exactly are not new, and
[recent work](https://arxiv.org/abs/2611.18114) shows that a frontier model can write them. The most
ambitious version, [Looped Weight-Space Programming](https://mbzuai-oryx.github.io/LoopedWSP/),
writes one small block and applies it as many times as the problem needs. That is a loop over depth,
in a network built for the task. The network does nothing else, and connecting such networks to a
language model is left as future work.

A pretrained model cannot loop over depth. Its 32 layers are all different and each runs once per
token. But it does repeat one thing: each token it writes is fed back in. If something inside the
model decides the next token, and that token changes what it decides next, the model is running a
loop. The memory of the computation is the text written so far. We call that text the tape.

<WeightsFigure name="loop" wide>

**Figure 2.** Two places a loop can live. A purpose-built network repeats one block over depth and
keeps its state inside. A pretrained model runs each of its layers once per token; its only loop is
that the token it writes comes back in, so the state has to live in the text.

</WeightsFigure>

## Tower of Hanoi is counting

To install a program we first have to put it in a form this loop can run: read a little, write one
token, repeat. Hanoi has such a form. Number the moves 1, 2, 3 and write each number in binary.
Adding one clears a run of trailing ones and then sets a single zero. That one bit names the disk
that moves, and each disk always travels the same way round the three pegs: odd disks one way, even
disks the other.

So a position of the puzzle fits in one cell per disk, holding that disk's peg and one bit of the
counter. To make a move, sweep across the cells carrying a one. While the carry meets a 1 it clears
it and travels on. Where it meets a 0 it sets it, moves that disk one peg round, and stops.

<WeightsFigure name="count" wide>

**Figure 3.** Four disks, fifteen moves. Each row is the move number in binary with the lowest bit
on the left, so column 1 is the smallest disk. Outlined cells are the ones the carry passed through;
the filled one is where it stopped, and that disk moves.

</WeightsFigure>

## The tape

Each cell is written as one token. A cell's token has to say three things at once: which column it
is in, what it holds, and whether the carry is still travelling when the sweep leaves it. We gave
every such combination its own token: 100 symbols for up to ten disks, plus one that halts.

The tokens are borrowed letters, and each column borrows from a different script: Hangul for the
first, Georgian for the second, and so on. The scripts do two jobs. A letter tells the head which
column it belongs to. And the machine can only fire when letters from two neighbouring columns
appear in one unbroken run, which ordinary text in any single one of these languages does not
produce.

What the model writes is therefore not a list of moves. It is the position of the puzzle after every
move, in these letters. Reading it takes a lookup table, and the model never translates it back.

<WeightsFigure name="alpha" wide>

**Figure 4.** The 100 symbols of the Hanoi program. A symbol's script gives its column, which is its
disk; its row gives the counter bit, the peg, and whether the carry travels on. Column 11 exists
only to end a ten-disk line.

</WeightsFigure>

## Inside the head

The first layer of this model uses a recurrent kind of attention.[^2] Each head keeps a small memory
that it updates at every token. It forms a key and a value from the current token and adjusts the
memory so that this key now returns this value. At full strength the adjustment replaces whatever
was stored under that key. Reading uses a query in the same way.

We took over one head, the one whose removal changes the model's predictions on ordinary text the
least, and gave each of its parts a job:

1. **Key.** The current symbol's column picks a memory slot.
2. **Value.** The symbol's contents go into that slot, replacing the column's entry from the
   previous line.
3. **Query.** The head reads the slot of the next column, which still holds last line's entry.
4. **Gate.** The model applies a gate to each channel of what was read. We use it as a selector: the
   current symbol opens only the channels for the column it asks about and the carry it brings.
   Exactly one channel is both open and non-empty. It stands for the pair "old contents, carry".
5. **Output.** The output matrix sends that channel to the embedding of the next symbol. This matrix
   is the program's table.

One more thing makes it work, and it comes back later. The head sits in the first layer with 31
layers above it. For its choice to survive them, the next symbol's embedding is written 20,000 units
long into a stream whose normal size at that point is about 3. Nothing the later layers add can
outvote it.

## Install, stack, uninstall

Because the program lives in one head, installing it changes 2.63 million of the model's 4.2 billion
numbers, about six in every ten thousand. The patch file holds only those rows. Applying it returns
what it overwrote, so uninstalling restores the model bit for bit.

<WeightsFigure name="scale" wide>

**Figure 6.** The patch, to scale. The small square has 0.06% of the large one's area.

</WeightsFigure>

The engine is not specific to Hanoi. A program is a table from "old contents, carry" to the next
symbol, so a different table is a different program. We wrote two more: Rule 110, a cellular
automaton in which each cell's next state depends on itself and its two neighbours, and a binary
adder for numbers up to ten bits. Both install into a second head with their own letters.

<WeightsFigure name="progs" wide>

**Figure 7.** Three programs on one engine, all with the patch. The panel above is a simulation of
the tables in your browser, not the model; the table gives what the model itself did, checked
against ordinary reference code. The smallest margin by which the right token won was 35 logits. The
ten-disk run is 11,264 tokens and took about fourteen minutes on a laptop.

</WeightsFigure>

## Against prompting and fine-tuning

The two ordinary ways to get a model to do something are to show it examples and to train it. On
this task neither extrapolates. Prompted with worked solutions, the unmodified model manages four
disks once in six attempts and nothing larger. Fine-tuned on the complete solutions for one to six
disks, it reproduces those and fails at seven and eight after 47 legal moves each: it has memorised
sequences, not learned the procedure.[^3] The patch has seen no examples, and works at every size
its tape can hold.

fine-tuned model writes moves and the patched model writes positions, so their outputs are graded
the same way, by replaying them, but they are not the same format. A dash means not tried.

</WeightsFigure>

## What it costs the host

Installed software should not break the machine. We compared the patched model's next-token
predictions with the unmodified model's on text unrelated to the program.[^4] On 51,200 tokens of
English prose and code, the two models agree on the most likely next token 98.5% of the time, and
the average KL divergence is 0.0023. Deleting the head and installing nothing gives the same two
numbers. On this text, the whole cost of the patch is the head it occupies. Two patches cost what
deleting two heads costs: 0.0074 and 97.0%.

Two cautions. The first is what 98.5% means in practice: about one token in 65 changes, and when a
model writes freely, one changed token can send the rest of a passage somewhere else. We had each
version continue 100 openings for 36 tokens. The patched model wrote the identical continuation for
55 of them. So did the model with the head simply deleted: free writing is sensitive to any change
at all. The second is text that uses the borrowed letters. On Wikipedia articles in the twelve
scripts, where one token in nine is a reserved letter, the patch costs 0.013 against 0.0032 for
deleting the head, four times as much, and most of all in Tamil and Arabic.

## The host cannot launch what it cannot see

Up to here a person types the first line. An installed program should be something the model can
start. Hanoi's call is short: an opening token, then the start line for the number of disks. We gave
the model a legend listing the start line for each size, two worked examples and a new question.

The unmodified model writes the call correctly every time. It then has to invent the run, and gets
it wrong. The patched model does worse. It writes the opening token and a few letters, and stops. It
never completes the start line.

The reason is the 20,000. A write that large decides the output, but it also swamps everything else
at that position, for every layer above it. To the rest of the network, a token that launched a run
no longer looks like anything. The worked examples in the prompt each contain such a token. The
model cannot see how they ended, so it cannot learn how to end its own.

<WeightsFigure name="blind" wide>

**Figure 10.** Why the patched model cannot launch its own program. With the patch, the token that
starts a run is unrecognisable from the first layer on: its similarity to the same token in the
unmodified model falls from 1 to about 0 and stays there, because the stream at that position is
several thousand times its usual length. The launchable build, described next, keeps it at 0.94 or
higher until the final layer.

</WeightsFigure>

## Write quietly, answer late

The fix keeps the computation in the first layer and moves the announcement to the last. The head no
longer writes an embedding. It writes two small numbers along reserved directions of the residual
stream:[^5] the index of the next symbol in a table, and a reference value of 0.5. Those directions
are removed from the output of every other component in every layer, so the two numbers reach the
top unchanged. They are also chosen at right angles to the embeddings of all the tape letters, so on
a tape token they hold exactly what the head wrote.

At the last layer a bank of neurons turns the index into a symbol. Pair _k_ switches on when the
index reaches _k_ and swaps symbol *k*−1 for symbol _k_. Ordinary tokens must not set it off, and
they carry a little along any direction just by having an embedding. So two relay neurons square the
reference on the way up. A real call's 0.5 becomes large; an ordinary token's stray 0.01 becomes
nothing.

This is no longer a one-head patch. Removing four directions from every writer touches the 64
matrices that hold about a quarter of the model's numbers, each by a small amount, and it costs
more: on the same 51,200 tokens, a KL of 0.016 and 96.0% agreement, about seven times the patch. On
Wikipedia text in the tape scripts it costs 0.0095, a little less than the patch does there. It
still ships as a file, 33 MB for two programs sharing one announcer, which rebuilds the edit on an
unmodified model. Uninstalling it restores the weights to within rounding (the largest difference is
1.5 parts in a hundred million), not bit for bit.

## The host launches the program

With the launchable build, the model writes the call, the program runs to its halt symbol, and the
model carries on. With the prompt shown below it did so for all six sizes we tried: 1, 3, 5, 6, 7
and 8 disks, the last a run of 255 moves and 2,300 tokens. On 24 general-knowledge questions in the
same format it answered correctly and never started the solver.

How well this works depends on how well the prompt teaches the call. We tried two more prompts. With
different wording and different worked examples, the unmodified model itself wrote the right start
line for only four of six sizes, and the launchable build launched exactly those four. With a bare
legend and a single example, the model found the right start line for one or two sizes out of nine,
and one run launched. In all, 11 of 21 attempts launched, and every run that started was exact to
its last token. The one-head patch launched none of the 21.

This is the model learning a call format from its prompt, not deciding unprompted that it needs a
tool: the legend and the examples are right there. What changed is that the model can now learn from
them.

We first found and fixed the problem on a smaller program, a checksum over a string of digits, whose
call is made of ordinary digit tokens. There the numbers are larger. Out of 60 questions, the
unmodified model working step by step gets 54 right. With the checksum written loudly at the first
layer, the model never completes a call and gets 12 right by guessing. Written quietly, it completes
the call and answers correctly 60 times out of 60, and on fresh numbers in three differently worded
prompts, 300 times out of 300. When 30 general questions are mixed in, it calls on all 30 checksum
questions and on none of the others.

One task still fails, and the failure is the host's. Asked whether a code's last digit matches the
checksum of the rest, the model calls every time and the program is right about what it is given.
But in 40 of 60 cases the model passes the whole code, not the code without its last digit.
Installing a program does not teach the model how to use it well.

## How a weight is written

Everything above depends on writing a weight row that reads a chosen value on one token and exactly
zero on a list of others. In the first layer this is possible because a token's input does not
depend on context: it is the token's embedding, normalised. Take the token's input vector and remove
from it the part that lies along each of the other tokens' vectors. What is left is a direction
private to that token. Scale it so that it reads 1 on its own token. A row that should read 20 on
these symbols and nothing on those is then a weighted sum of private directions.

<WeightsFigure name="method" wide>

**Figure 13.** The one primitive. With two tokens it is a picture: remove from A's input the part
along B. The real version removes 285 other directions from each of 286 reserved tokens, in 2,560
dimensions.

</WeightsFigure>

Ordinary tokens are handled differently, since there are 248,000 of them. The head's keys and
queries are normalised to unit length, so we add channels that read zero on tape letters and very
large on everything else. An ordinary token's key and query then point almost entirely into those
channels and away from the memory.

Two choices sit near the edge of the rule and should be stated. Private directions are arithmetic,
but building them amounts to solving a small linear system. And for the launchable build, the
directions to reserve were chosen by clearing candidates one at a time and measuring the cost on
ordinary text: a search over where to write, never over what.

## Related work

The rule comes from
[Language Models Can Rewrite Their Own Weights](https://arxiv.org/abs/2611.21885), which has a model
edit itself with no gradients and asks that "every value" in an edit be "written by the model's own
reasoning". Its edits are coarse and remove obstacles; none installs a new behaviour. Looped
Weight-Space Programming runs far harder programs than ours, mazes, Sudoku and a million-move Hanoi,
in networks written from nothing. What is different here is the host: the program goes into a
pretrained model that keeps working, through its normalisation layers and in its existing tensors,
and the model can be the one to start it.

## Limits

- **The launchable build costs several times more than the patch** on ordinary text, and its
  uninstall is exact only to rounding. All three programs run on it, and two can share one
  announcer, but with two the narrowest winning margin fell to 1.8 logits, so that table is close to
  its limit.
- **Launching depends on the prompt.** Six of six with our main prompt, four of six and one of nine
  with two others. The model has to be taught the call, and a 4B model is easily confused about it.
- **Half precision breaks both builds.** Rounded to the 16-bit format the model ships in, the patch
  gets 446 of 640 tokens right and the launchable build 19 of 320. They need the model loaded at
  full precision.
- **The output is a tape, not an answer in words.** The model never converts it to moves.
- **Small scale.** This build gives the tape 11 columns, so Hanoi stops at ten disks, and it writes
  about 14 tokens a second.
- **One model.** Everything here is one 4B checkpoint whose first layer happens to have a recurrent
  memory. We have not tried another architecture.
- **Not written by the model.** A larger model and a person wrote these edits over many attempts,
  with tests in the loop.
- **The same method could hide a trigger, though not quietly.** A patch that ordinary evaluation
  barely registers is also a way to plant behaviour. These edits are trivial to find in the weights:
  the largest weight in the model as shipped is 0.7, and the patch contains weights of 93,000. We
  have not tried to make them hard to find.

## Appendix: what broke along the way

**A zero is not zero.** The design needs some weights to read exactly zero on certain tokens. Stored
as 32-bit floats they read about one part in ten million instead, and the head multiplies whatever
it reads by the size of its write. On a test page we wrote in the twelve scripts, that turned
rounding error into wrong predictions. The cure was to make "off" a firmly negative value, where the
activation function is flat, and only for the program's own symbols. Doing it for every token
switched the machine on for common English words and cut agreement with the original model to 40%.

**The quietest directions were the expensive ones.** For the launchable build we first reserved the

predicted the cost, so we measured it. Four chosen that way cost 0.0033 together.
